# 작성 원칙

## 1. 기본 전개

1. 구체적인 문제로 시작한다. 정의부터 나열하지 않는다.
2. 원리와 성립 조건을 설명하고, 손으로 추적할 수 있는 작은 예제를 둔다.
3. 직접 구현하고 대안과 비교 실험한다. 효과가 없었던 실험도 기록한다.
4. 한계와 선택을 바꿀 조건으로 마무리한다.

학습 완료 기준: 정의 설명, 코드 추적, 실험 재현, 실패 조건 설명을 모두 할 수 있는가.

## 2. 말투

기준 원고는 직접 수정한 `pdps-tech-blog/posts/01-background.md`이다. 아래는 그 글에서 뽑은 규칙이며, 새 원고를 직접 고치면 이 목록을 갱신한다.

- 종결은 `~다`, `~이다`, `~한다`의 평서문이다. `~해요`, `~습니다`, 명사형 종결(`~함`, `~임`)은 쓰지 않는다.
- 첫 문장은 실제 상황을 담담하게 서술하며 시작한다. 인사나 "오늘은 ~에 대해 알아보겠습니다" 식 도입은 쓰지 않는다.
- 도입에서 이번 글이 다루는 범위를 한 문장으로 밝힌다. 예: "이번 글에서는 ~를 정리한다."
- 문장은 한 문장에 하나의 사실을 담고, 길어지면 나눈다. 보통 40~80자 안팎이다.
- 개념을 말한 뒤 바로 "예를 들어"로 구체 사례를 붙인다.
- 1인칭은 필요할 때만 "나는"으로 쓴다. 글 전체에 반복하지 않는다.
- 접속은 "따라서", "그렇기에", "또한", "이처럼" 정도의 평범한 연결어를 쓴다.
- 보충 설명은 괄호로 짧게 붙인다. 예: (int, float 등)
- 굵은 글씨는 글 전체에서 핵심 한두 곳에만 쓴다.
- 표는 단계·비교를 한눈에 보여줘야 할 때 글당 하나 정도만 쓴다.
- 확인하지 못한 것은 "확인하지 않았다"고 쓴다. 성과는 측정 조건과 함께 쓴다.

## 3. AI 티 방지

초안을 쓴 뒤 아래 항목을 찾아 고친다.

- 대조 구문: "단순한 X가 아니라 Y이다", "X뿐만 아니라 Y도" 를 반복해서 쓰지 않는다.
- 3개 나열 습관: 항목이 실제로 둘이나 넷이어도 억지로 셋으로 맞추지 않는다.
- 과한 비유와 수식어: "핵심", "강력한", "혁신적인", "마법 같은", "한 단계 더" 등.
- 상투적 연결과 마무리: "결론적으로", "중요한 점은", "이를 통해 알 수 있듯", "마지막으로 정리하면", 마지막 문단의 교훈 요약.
- 독자에게 거는 말: "함께 알아봅시다", "궁금하셨죠?", "~해 보세요".
- 장식: 이모지, 이유 없는 굵은 글씨, 소제목 남발, 문장마다 줄바꿈하는 목록.
- 근거 없는 단정: "가장 효율적인", "반드시", "항상". 조건과 수치를 붙이거나 표현을 낮춘다.
- 정의 나열로 분량 채우기: 같은 말을 표현만 바꿔 반복하지 않는다.
- 내용 없는 대칭: 장점과 단점을 개수만 맞춰 쓰지 않는다. 실제 실험에서 나온 것만 쓴다.

확인 방법: 각 문단이 빠져도 글이 성립하는지 본다. 성립하면 그 문단은 지운다.

## 4. 글 의도별 전개

글을 쓰기 전에 의도를 하나 정하고, 해당 뼈대를 따른다. 한 글에 의도가 둘 이상이면 주된 하나를 앞에 둔다.

### 개념 설명 (이론)
문제 상황 → 개념의 정의와 성립 조건 → 작은 예제 손 추적 → 직접 구현 → 한계와 쓰이지 않는 조건

### 구현 기록
만들려는 것과 제약 → 접근 방법과 선택 이유 → 구현 핵심 코드 → 동작 확인 → 남은 문제

### 비교 실험
질문 → 비교 대상과 기준 → 실험 조건(입력 크기, 환경, 반복 횟수) → 결과 표 → 해석 → 결과가 뒤집히는 조건

### 삽질·실패 기록
증상 → 처음 세운 가설 → 확인 과정 → 원인 → 수정과 재발 방지 → 처음 가설이 틀린 이유

### 복습 정리
이 주제를 왜 다시 정리하는가 → 핵심 개념 3~5개 → 서로의 관계 → 아직 모르는 것

## 5. 사실의 구분

- 직접 구현하고 측정한 것과 책·문서에서 읽은 것을 구분해서 쓴다.
- 비교하지 않은 후보를 비교한 것처럼 쓰지 않는다.
- 출처는 글 끝 "참고 자료"에 모은다.
